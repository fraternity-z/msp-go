# Go 数据库迁移策略

`backend/migrations/` 是当前数据库结构的唯一迁移来源。首次生产发布前的开发迁移已收敛为四个最终态基线分组，后续能力只通过连续的增量迁移追加：

| 版本 | 分组 | 内容 |
|------|------|------|
| `0001_initial_schema` | 基础结构 | 身份、班级、内容、学习、DKT、AI 配置和安全 |
| `0002_student_ai_safety` | AI 风控 | 学生访问控制、用量统计和模型审核 |
| `0003_communication` | 站内通信 | 公告、私信、通知、答疑、快照触发器和附件 |
| `0004_delivery_integrations` | 外部通知 | 微信绑定与提醒任务、邮件模板 |
| `0005_daily_question` | 每日一题 | 固定日题、班级策略、题目日程、公众号提醒和统计 |
| `0006_portrait_report_scope` | 画像报告范围 | AI 画像解读的统计范围与数据快照时间 |
| `0007_portrait_revision` | 画像并发控制 | AI 画像生成与删除使用的乐观并发修订号 |
| `0008_student_portrait_actions` | 画像行动 | 学生显式开始的画像练习行动及 DKT 尝试次数基线 |
| `0009_daily_question_integrity` | 每日题一致性 | 作答幂等绑定、提醒并发约束、统一题冻结排期、日程版本和历史名册 |
| `0010_mistake_review_tasks` | 错题本完整闭环 | 复习任务、题面快照、三类提交幂等、聚合归档、掌握度权重、知识点校准、DKT/画像一致性和全部作答题面冻结 |
| `0011_forum_center` | 全站论坛 | 论坛板块、帖子、回复、点赞、收藏、举报、精选、互动通知及查询索引 |
| `0012_learning_session_mode` | AI 学习会话模式 | 模式独立持久化、旧标签精确回填和取值约束 |
| `0013_session_first_chat_idempotency` | AI 首轮会话幂等 | 首次请求不可变摘要、确定性助手消息及可超时接管的生成 claim |
| `0014_ai_generation_defaults` | AI 生成参数 | 停用 Top P，并校准 Temperature、Max Tokens、超时和重试默认值 |
| `0015_auth_version` | 认证会话失效 | 为账户增加认证版本，使密码和状态变化立即撤销既有 access/refresh token |
| `0016_local_upload_access` | 本地上传授权 | 记录本地对象上传者，并为消息附件与公开资源授权查询增加索引 |
| `0017_resource_vector_foundation` | 资源中心向量基础 | 默认租户/知识库、文档版本/chunk、ACL、embedding model version、索引 generation、可靠 job，以及扩展 transactional outbox |

`0001` 至 `0004` 是空库基线，`0005` 交付每日一题，`0006` 至 `0008` 交付学生画像增量能力，`0009` 在不重写版本 5 的前提下补充每日题提交幂等、统一题排期一致性和成员历史结构。远端共享迁移链只到 `0009`，工作区中的四个未发布草稿已按依赖顺序合并为单一 `0010`：先拆分错题的不可变作答证据与可变复习计划，再补齐普通作答、正式复习和历史重做的独立幂等契约及复合归属约束，随后校准 DKT、画像和知识点持续约束，最后为全部已提交作答冻结题目属性。

`0010` 将题目、每日题、复习任务和作答快照中的知识点校准为引用真实节点的非空 JSON 数组，无法分类的集合统一归入系统“未分类”节点；它只为每个学生、每道题最新仍未解决的错误回填任务，已经被后续正确作答解决的历史错误仍保留为证据但不会重新进入计划。既有作答保留默认全权重 `1`，不会依据历史请求来源追溯重分类。迁移前已有正式复习 key 因无法可靠还原原请求摘要而写入保留值，旧 ID 重试会返回冲突。只有全部历史交互都能由不可变证据解释时才执行 DKT 回放；其余旧普通作答仅用迁移时可取得的最佳题面建立稳定快照，不声称恢复原始版本，也不据此重算掌握度。迁移 9 对迁移前已离班且从未产生 assignment 的成员仍无法恢复历史名册。已经进入共享分支或被任一共享数据库执行的版本均视为不可改写历史。

`0011` 在消息中心增加全站论坛数据模型，并预置高等数学、线性代数、概率统计、学习方法、资源分享和平台反馈六个板块。论坛互动通知独立持久化，但未读数量与最近互动会合并进入学生和教师既有的消息中心摘要；API 进程不会自动执行该迁移，部署时必须先迁移再启动新版本。

`0012` 为 AI 学习会话增加独立 `mode` 字段，避免模式切换继续覆盖用户可见的 `current_topic`。迁移只对“学习模式、练习模式、讲解模式、聊天模式”四个精确旧标签做确定性回填，其余历史会话采用 `chat` 默认值；更新已有环境时必须先停止或排空仍按旧字段写入的 API 实例，完成可恢复备份后执行迁移，再依次启动读取 `mode` 的新 API 和前端版本，禁止新旧写入逻辑混跑。

`0013` 为首次发送保存不可变请求摘要、确定性助手消息 ID 和带过期接管语义的 claim。会话、欢迎语、首条用户消息和幂等元数据在同一短事务中创建；模型调用不占用数据库事务，只有持有当前 claim token 的请求才能在独立短事务中原子保存助手回复、可选用量记录和完成时间。请求取消或完成事务失败时会按 token 主动释放 claim，进程中断等无法主动释放的情况才等待绝对过期时间后接管。部署时必须先执行迁移，再启动调用首次聊天幂等接口的新 API。

`0014` 清空模型和智能体中遗留的 Top P，但暂时保留 nullable 数据库列以支持旧版本读取和回滚；新运行时不再向 provider 发送 Top P。迁移只把仍等于旧生成默认值的数据校准为 Temperature `1.0`、Max Tokens `4096`、超时 `1800` 秒和最大重试 `3` 次，其他显式自定义值保持不变。前三个非超时数值是管理员开启覆盖时的基线：Temperature 和 Max Tokens 留空时不发送，最大重试留空时为 `0`，不会因为数据库保存了建议值就自动启用。部署时先停止或排空旧 API 写入、备份数据库、执行迁移，再启动不再使用 Top P 的新 API。

`0015` 为每个账户增加从 `1` 开始的 `auth_version`。新 API 签发 access/refresh token 时固化该版本，并在每次受保护请求和刷新时与数据库当前值核对；自助改密、管理员重置密码、密码重置审批和账户状态切换会原子递增版本。旧版令牌不含该 claim，迁移后会被统一拒绝，所有用户需要重新登录。部署必须排空并停止旧 API、备份、执行迁移后再一次性启动新 API，不能让仍签发无版本令牌的旧实例与新实例混跑。

`0016` 新增 `local_upload_objects`，记录新本地对象的 URL 与上传者；同时为私信、答疑、公告、论坛、AI 会话附件 JSON 和资源 URL 增加索引。迁移不自动回填历史 URL，因为既有附件与资源字段可由客户端提交，无法据此证明原始上传者；缺少可信所有权记录的历史本地文件保持 `404`，只能由用户重新上传，或通过单独评审、可审计的数据导入建立所有权。新 API 对 `/uploads/` 默认拒绝，只允许上传者或由该上传者创建的合法业务引用放行给消息对象参与者/收件人、可见论坛内容查看者及已发布资源查看者，避免其他用户通过重复引用私有 URL 洗白权限。必须先执行迁移，再启动启用本地上传授权的新 API。

`0017` 为资源中心建立显式 `default` tenant/knowledge base，并将现有 `contents` 确定性回填到该租户和默认 membership；`contents.tenant_id` 同时设置相同的列默认值，以兼容尚未传租户字段的旧资源/题目/练习写入链路。它不宣称完整多租户能力。新增的文档、不可变版本、资产、chunk、模型版本、generation、vector manifest 和 `resource_processing_jobs` 均使用 PostgreSQL 作为事实来源，时间字段按 UTC 无时区约定保存。`outbox_events` 增加 available/lease/heartbeat/dead、错误码、幂等键和最大重试字段，旧事件的 `available_at` 回填为原 `created_at`。本迁移不创建 Qdrant collection、不写入向量，也不启用异步 worker；后续 P2 从这些契约继续追加。部署前仍需备份并在一次性空库和现有基线库上验证约束、回填和重复迁移行为。

## 基线兼容边界

- 全新数据库按 `0001` 至 `0017` 执行，首次记录版本 `1` 至 `17`；version 16 数据库只应用 `0017`，version 15 数据库依次应用 `0016`、`0017`，更早版本仍按版本号顺序补齐全部后续迁移。
- migration runner 会同时校验版本号和迁移名称，并拒绝应用记录与当前代码不一致或包含未知版本的数据库。
- 执行过重整前旧开发迁移链的临时数据库（该旧链也曾占用 `0001` 至 `0015`，但迁移名称和内容不同）必须删除并重建，不能通过修改 `go_schema_migrations` 记录使其伪装为当前基线。
- 曾执行工作区旧草稿 `0010` 至 `0013` 的本地数据库已经具备最终结构，但迁移账本与当前单文件链不兼容。可丢弃的库应重建；不可丢弃的库必须先停止写入并备份，完整核对最终结构后才能在排他锁内做仅迁移元数据的收敛，禁止删除 version 10 后重放合并迁移。
- 曾以 `0011_mistake_book_integrity` 执行旧错题本草稿的本地数据库与当前 `0011_forum_center` 同号冲突。论坛迁移继续保持规范版本 `0011`，不能改号、重命名已执行记录或放宽 runner 校验；可丢弃的开发库应重建，不可丢弃的库必须先停写、备份并核对其错题结构已被当前 `0010_mistake_review_tasks` 完整覆盖，再通过单独评审的数据保留校准方案收敛迁移元数据。
- 曾把每日题完整性迁移以本地开发版本 `0006` 执行的数据库与当前 `0006_portrait_report_scope` 历史冲突，不能直接重放；可丢弃的开发库应重建，不可丢弃的数据库必须先核对实际结构和迁移账本，再设计、评审并验证数据保留校准方案。
- 对不可丢弃的旧数据库，应停止发布并单独设计、评审和验证数据保留迁移。
- 后续结构或数据变化从 `0018` 起追加，不再重写已发布或已共享的 `0001` 至 `0017`。

### 旧本地错题迁移账本校准

仅当不可丢弃的本地开发库完整执行过旧草稿链的已知形态时，才可使用专用校准命令：账本包含版本 `1` 至 `11`（只跑到 `11_mistake_book_integrity`），或包含完整的旧版本 `10` 至 `13`。执行前必须停止所有应用写入，创建 `pg_dump --format=custom` 备份，并用 `pg_restore --list` 验证备份可读。该命令只允许 `development` / `dev` / `local` / `test` 这些显式本地环境名，任何其他环境名均拒绝；它也不适用于缺少版本、名称不同、存在额外版本或 schema 断言不通过的数据库。

在 `backend/` 目录依次运行：

```powershell
go run ./cmd/migrate-reconcile --check
go run ./cmd/migrate-reconcile --apply --confirm RECONCILE_0011_MISTAKE_BOOK_INTEGRITY
go run ./cmd/migrate
go run ./cmd/migrate
```

`--check` 及无参数调用都只读，但检查事务也会短暂取得迁移账本排他锁；`--apply` 会在相同排他锁和完整断言通过后，只删除校验过且名称精确匹配的旧版本 11（如果存在则同时删除旧版本 12、13）元数据，不修改保留的 version 1 至 10 记录。它不会执行、创建或重放任何迁移 SQL，也不会修改业务表或业务数据。第一次普通迁移随后应按版本顺序应用全部待执行的规范迁移（当前为 `0011_forum_center`、`0012_learning_session_mode`、`0013_session_first_chat_idempotency`、`0014_ai_generation_defaults`、`0015_auth_version`、`0016_local_upload_access` 和 `0017_resource_vector_foundation`，未来新增版本也一并应用），第二次应返回 `applied_count=0`。任一检查失败时不得手工删除或改名账本记录，应恢复写入前状态并单独评审实际历史。

## 新增迁移

- 文件名使用 `NNNN_description.up.sql`，版本号连续且一经发布不可复用。
- 不修改已共享或已执行的迁移来承载增量变化，也不重建已经发布的迁移历史。
- 每个迁移保持单一目的，明确约束、索引、默认值和数据修正的执行顺序。
- 结构或数据变更必须经过评审；禁止在没有迁移记录的情况下直接修改共享数据库。

## 执行与验证

在 `backend/` 目录运行：

```powershell
go run ./cmd/migrate
go run ./cmd/migrate
```

全新空库首次执行应记录当前全部嵌入版本，紧接着重复执行应为 `applied_count=0`。后续版本首次执行记录实际待应用数量，重复执行仍必须为 `0`。发布前还应在一次性空库验证关键表、约束、索引、默认值和种子数据。

## 发布与回滚

- 已有环境先停止或排空应用写入，再创建并验证可恢复备份；迁移成功后才启动依赖新结构的 API 版本。
- migration runner 不由 API 自动执行，部署流程必须显式运行。
- 不提供自动 down migration；失败时恢复备份，或发布经过评审的补偿性 forward migration。
- 回滚应用镜像前，先确认旧版本能够读取迁移后的结构。
- 仓库外数据库若执行过未发布、旧开发链或不同内容的同版本迁移，先核对实际 schema 和 `go_schema_migrations`，不得通过删除版本记录盲目重放。

历史 Alembic 链已退出当前工作区；需要追溯时使用 Git 历史或已归档的发布材料。
